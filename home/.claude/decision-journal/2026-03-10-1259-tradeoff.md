## Decision Summary

The session identified that the standup aggregation script's PR tracking was limited to the current repository. The key decision was switching from `gh pr list` (repo-scoped) to `gh search prs` (cross-repo search) to capture PR activity across all repositories.

## What Was Chosen

Switch from `gh pr list` to `gh search prs` for PR data collection:
- Use `gh search prs --author=@me --merged --limit 50 "merged:$YESTERDAY"` for merged PRs across all repos
- Use `gh search prs --author=@me --limit 50 "created:$YESTERDAY"` for opened PRs across all repos
- Use `gh search prs --review-requested=@me --state=open --limit 20` for pending reviews across all repos

## Alternatives Considered

1. **Repo-scoped approach** (current): Use `gh pr list` with repo-scoped queries - only captures PRs in the current repository
2. **Manual GitHub API calls**: Call GitHub REST API directly for cross-repo queries - adds complexity and error handling burden
3. **Shell script aggregation**: Loop through known repos and call `gh pr list` in each - brittle and maintenance-heavy

## Trade-offs

- **Scope vs. Maintainability**: `gh search prs` searches all accessible repos (broader scope) but requires different command syntax than `gh pr list` (slightly different learning curve)
- **Completeness vs. Performance**: Searching across all repos may return more results; the `--limit` flag keeps performance acceptable
- **Date Syntax**: `gh search prs` uses different date format ("created:$YESTERDAY") vs `gh pr list` ("created:>=$YESTERDAY created:<$TODAY"), requiring adjusted date range logic

## Principles Applied

- **Right tool for the job**: GitHub CLI has search functionality purpose-built for cross-repo queries; using it is more appropriate than building custom solutions
- **Scope clarity**: Recognizing that `gh pr list` is inherently repo-scoped guided the decision to use the search API instead
- **API knowledge**: Understanding the distinction between scoped and global commands prevented building on the wrong foundation

## Revisit If

- GitHub CLI changes the API for `gh search prs`
- Performance becomes an issue (need to adjust `--limit` values or add result pagination)
- Requirements change to track PRs only in specific repos (would revert to `gh pr list` with targeted logic)
